### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge and verify each change independently.** Use the [Codex runtime](../references/codex-runtime.md#forge). Assign an independent verifier the exact base and head and the project verification skill or available driver. Keep reproduction writes in its assigned worktree. Record PASS, PASS+NOTES, or FAIL with runnable evidence on the real surface. An author, CI alone, and an approving bot review cannot satisfy this verification step. Stop before merging if the required independent verifier could not run.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up on GitHub.** Only after the operator has authorized merging, verify the PR's current head and base. Merge the lowest eligible PR with gh pr merge --squash, the resolved repository, and --match-head-commit for the verified head. Confirm state and base after the request. If the forge queued the merge, keep watching that same PR. Retarget the next PR from its merged parent branch to trunk and move its patch onto the merge result only as authorized, then recheck its proof and CI. Follow step 3 if the head changed. GitLab uses the single-MR procedure below.
5. **Observe the GitHub queue.** Run the bundled watch-pr with --queued-stack, --stack-prs set to the frozen bottom-to-top list, and a finite --timeout. Reuse that list on a later invocation. A move to trunk after a parent merge is expected. Inspect a blocker before changing anything. COMPLETE means the captured run finished.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

#### Single GitLab MR

Verify the exact MR head and intended target branch, independent test evidence, required approvals, discussions, and head pipeline through the resolved GitLab project. Require the operator's authorization and a ready watcher verdict before a merge. Use glab mr merge with the resolved project URL, verified IID, --sha set to the reviewed head, and --auto-merge=false. Re-read the MR until the forge confirms the merge. Process a single MR only. Report a request for automated GitLab stack handling as unsupported.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
